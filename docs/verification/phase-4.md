# Phase 4 manual verification (2026-11-11)

Produced by the Task 10 verification pass. This task is docs-only (the checklist plus a
cross-reference repair), so no automated section is recorded here — the suite/bundle/
launch smoke checks are the lead's final-verification pass per the plan (`swift test`,
expected ≈230 passing; `./Scripts/make_app.sh`; launch with and without `--safe-mode`).
Every item below needs the app running against real hardware: an owned multi-button or
specialty device (a mouse whose extra buttons never surface as CGEvents, a pedal, a
trackball, a free-spin wheel, or a mouse with a vendor DPI report) for items 2, 3, 7,
8, 9, 11 and 14; a plain mouse with working buttons 6+ and a stock wheel covers the
rest. Items are numbered and left unchecked with a HOW TO VERIFY line each.

## Human checklist

- [ ] 1. Buttons 6–32 that surface as CGEvents bind and fire; Phase 4 changes nothing about their behavior.
  HOW TO VERIFY: Settings → Buttons → "Add…" must offer Button 6 through Button 32; add one (e.g. Button 6), bind it to a visible action (Mission Control), and press that physical button on a mouse whose extra buttons already work in macOS — the action must fire exactly once per press, the row must survive a relaunch, and an unbound extra button must still act stock.
- [ ] 2. A device profile with "Capture extra buttons as raw HID" ON for a mouse whose buttons DO surface fires every such press TWICE — the documented failure mode (Review Focus 1) as the expected consequence of the misconfiguration — and the UI warns about exactly this in the profile editor.
  HOW TO VERIFY: Devices tab → Edit Profile… on that mouse's profile, toggle "Capture extra buttons as raw HID", Save; bind its Button 6 to a visible action and press it — the action must fire twice per press. With the profile editor open, the orange caption under Extra Buttons must read "Only for mice whose extra buttons never reach macOS. If your buttons already work, enabling this fires each press twice." Turn the toggle back off — single fire returns.
- [ ] 3. A device-profile part (vendor button or pedal) fires its binding; the part name appears as a caption on the Buttons tab.
  HOW TO VERIFY: Devices tab → Edit Profile… → Add Part, give the part a name (e.g. "Thumb 1"), keep kind Button (or pick Pedal for a pedal), enter the element's page/usage coordinates (discover them with the analyzer, item 4), pick a "Routes as" number, Save; bind that button number on the Buttons tab; press the physical part — the binding must fire, and the Buttons tab row for that number must show the part's name as its caption.
- [ ] 4. The Device Analyzer streams live entries while a button/wheel is exercised, filtered to that device; Clear empties the view.
  HOW TO VERIFY: Devices tab → Analyze…; press buttons and roll the wheel — monospaced lines of the shape `page 0x9 usage 0x10 value 1` (newest first) must appear live for this device only; click Clear — the list must empty; press again — fresh entries must appear; Done closes the sheet.
- [ ] 5. Device Log persists to ~/Library/Application Support/artMouse/devices.log while toggled on, and stops when untoggled.
  HOW TO VERIFY: Analyze… the device, exercise it with "Save to log file" off and confirm the file is not written; switch the toggle on and exercise again — `tail -f ~/Library/Application\ Support/artMouse/devices.log` must show it growing with lines of the shape `<ISO8601 time> vid=… pid=… page=0x… usage=0x… value=…`; switch it off and exercise — the file must stop growing. (The toggle is a session switch, not a settings.json field, so it starts off again after a relaunch.)
- [ ] 6. A disabled device stops producing routed traffic on the HID side; the analyzer keeps recording it (the analyzer is a diagnostic), and CGEvent-tap-delivered events from that device still arrive — a known limitation.
  HOW TO VERIFY: flip the row's Enabled switch off, then press a part-bound or raw-captured button on that device — its binding must no longer fire (HID-side routing is dropped); open Analyze… — entries must still stream for it; press one of its standard buttons that already surfaces in macOS — that binding still fires, because the CGEvent tap path does not consult the Enabled switch. Re-enable and confirm HID routing resumes. The switch also works for devices without a profile (it is settings-key based and persists).
- [ ] 7. DPI on an owned device (a profile with DPI configured): DPI Up/Down/Cycle step the levels, Default returns to level 0, and the level persists across restart.
  HOW TO VERIFY: Edit Profile… → enable "Configure DPI feature reports" (levels default 800/1600/3200) and enter the vendor's report layout (Report ID / Value byte / Value mask / Report length — vendor-specific, per the editor's caption); bind buttons to Device → DPI Up, DPI Down, DPI Cycle and Default DPI; press them — sensitivity must step up, step down (clamped at both ends), cycle with wraparound, and Default DPI must return to level 0 (the first configured level). Confirm persistence with `python3 -I -m json.tool ~/Library/Application\ Support/artMouse/settings.json` (the profile's `activeLevelIndex`) and that a relaunch keeps stepping from the stored level.
- [ ] 8. DPI on a device without a DPI config degrades to cursor-speed profile switching: Up/Down/Cycle advance to the next profile and Default selects the profile named "Default".
  HOW TO VERIFY: on a device with no DPI section (or a device whose report send fails), bind Device → DPI Up/Down/Cycle/Default DPI and press them — the cursor speed must step through the profiles defined on the Cursor tab (watch the highlighted row) and Default DPI must land on the one named "Default"; no feature report may be attempted.
- [ ] 9. DPI Shift (hold): one level higher while held, back to the pre-shift level on release.
  HOW TO VERIFY: with a multi-level DPI config active, bind Device → DPI Shift, hold the button while moving the mouse — sensitivity must rise one level for the duration of the hold and return to the previous level the instant it is released; repeated taps must not creep upward. At the top level the hold must do nothing rather than wrap.
- [ ] 10. Trackball flip: horizontal scroll reverses while the General-tab toggle is on.
  HOW TO VERIFY: with a wheel profile active (any mode) on the Wheel tab, roll a trackball (or any horizontal pan source) left/right in a scrollable page; tick "Flip trackball horizontal direction" on the General tab and roll again — horizontal movement must go the opposite way; untick it and confirm the original direction returns. (The flip applies to intercepted horizontal events, so it needs an active wheel profile.)
- [ ] 11. Free-spin momentum on a free-spin wheel (constant mode): the page coasts after the spin stops, the coast is capped, new input kills it, and keys/auto modes never coast.
  HOW TO VERIFY: on a Wheel profile set mode Constant, enable "Free-spin momentum" (Coast decay % default 70, Coast max notches default 30) and flick a free-spin wheel hard in a long page — scrolling must continue and visibly decay after the wheel stops, never running longer than about Coast max notches; roll the wheel again mid-coast — the coast must die instantly and restart only from the new input. Then switch the same profile to Keys (wheel→keys) and to Auto mode with the toggle still on — neither may coast (keys stop when the wheel stops; auto stops after its configured silence ticks); acceleration mode must likewise never coast.
- [ ] 12. Settings round-trip: export → import carries device profiles, and an old Phase 3 settings.json still loads with defaults for the new fields.
  HOW TO VERIFY: General tab → Export Settings… with at least one device profile and a disabled device present; quit the app, delete or hand-corrupt settings.json, relaunch, then Import Settings… from the exported file — the device profiles (parts, DPI config, capture flag), the disabled-device list and the trackball flip state must all come back and survive a relaunch. Separately, with the app stopped, drop in a Phase-3-shaped settings.json (no deviceProfiles/disabledDeviceKeys/trackballHorizontalFlip keys, wheel profiles without momentum keys) and launch — it must load without warnings, with no device profiles, no device disabled, the flip off and momentum inert (defaults 70 % / 30 notches, unused); pinned by `SettingsStoreTests.testPhase2WheelProfileJSONDecodesWithMomentumDefaults` and `testTrackballFlipDefaultsFalseOnOldSettings`.
- [ ] 13. Sleep/wake and hot-plug: HID observation survives wake, and unplug/replug of a profiled device keeps its bindings working.
  HOW TO VERIFY: with a part or raw-capture binding active, sleep the Mac from the Apple menu, wake it, and press the bound part as the first action — it must fire with no relaunch. Then unplug the profiled device, confirm it disappears from the Devices tab (the list refreshes about every 2 s), replug it, confirm it reappears with its profile and Enabled state intact, and press the bound part — it must fire again with no relaunch or profile edit.
- [ ] 14. Devices → "Edit Profile…" → parts editor: a part-bound button/pedal fires its binding, and the Buttons tab shows the part's name as a caption.
  HOW TO VERIFY: Devices tab → Edit Profile…, in the Parts section Add Part, name it (e.g. "Pedal L"), set kind Pedal (or Button), fill the element's page/usage from the analyzer (item 4) and a free "Routes as" number, Save; bind that number on the Buttons tab; step on the pedal (or press the vendor button) — the binding must fire, and the Buttons tab row for that number must show "Pedal L" as the caption under it. (Same contract as item 3, exercised through the parts editor UI; the caption comes from the profile part name.)
- [ ] 15. Devices → "Analyze…" → the "Save to log file" toggle appears in the analyzer sheet header and switches device-log file persistence on/off — the file grows at ~/Library/Application Support/artMouse/devices.log while on and stops growing when off.
  HOW TO VERIFY: Devices tab → Analyze… — the sheet header must show the device name ("Analyzing …") with the "Save to log file" switch next to Clear and Done; exercise the device, note the byte size of ~/Library/Application Support/artMouse/devices.log (`ls -l`), switch the toggle on and exercise — the file must grow; switch it off and exercise — the size must freeze. (Same persistence contract as item 5, verified from the sheet header UI.)
